# Task 003 — Вебімпорт системних і приватних тем та слів English Cards

**Файл у репозиторії:** `docs/tasks/003-vocabulary-import.md`  
**Статус:** заплановано; Етапи 1–5 не розпочато  
**Дата створення:** 02.11.2026  
**Проєкт:** English Cards — Laravel 13 / PHP 8.4 / MySQL / Docker Compose (WSL2)  
**Тип:** full-stack / CSV import / access control / UI

## 1. Мета та очікуваний результат

Реалізувати **один вебінструмент CSV-імпорту** для всіх авторизованих користувачів English Cards:

- **Звичайний користувач** може імпортувати слова тільки до **приватних тем свого акаунта**.
- **Адміністратор** може робити **такий самий приватний імпорт для себе** або явно вибрати **імпорт системних тем**, видимих усім користувачам.
- Для адміністратора **тип за замовчуванням — приватний**. Системний імпорт — окремий усвідомлений вибір у формі й обов'язкове повторне підтвердження перед записом.
- Обидва режими використовують **один парсер, правила валідації, сервіс імпорту та інтерфейс**; відрізняються перевіркою прав і власником теми.

**Результат після всіх етапів:** користувач відкриває сторінку «Імпорт слів», завантажує CSV, бачить перевірку та попередній результат, підтверджує запис і отримує звіт. Імпорт повторюваний і безпечний, не створює зайвих глобальних слів/зв'язків та не змінює прогрес навчальних профілів. На локальному сайті й на production використовується **той самий вебсценарій** — без обов'язкової Artisan-команди, SSH, коміту CSV чи спеціальної адмінпанелі.

**Межі:** це імпорт, а не CRUD словника. Редагування/видалення тем і слів, зміна наявних перекладів, злиття/перейменування тем, імпорт прикладів/зображень, історія імпортів, ролі/permissions у БД, фонові черги, навчальні картки та синхронізація прогресу — **не входять** у Task 003.

## 2. Погоджена поведінка та контракт CSV

### 2.1. Режими імпорту

| Хто виконує | Режим | Значення `topics.user_id` | Хто бачить створені теми |
|---|---|---|---|
| Звичайний користувач | Приватний | `auth()->id()` | Усі навчальні профілі **його** акаунта |
| Адміністратор | Приватний (**за замовчуванням**) | `auth()->id()` | Усі навчальні профілі **його** акаунта |
| Адміністратор | Системний (вибирається окремо) | `NULL` | Усі користувачі застосунку |

- **Немає «системних слів» як окремого типу записів `words`.** Глобальні картки спільні; системність визначається **темою** через `topics.user_id IS NULL`.
- Ні CSV, ні клієнтський запит не визначають довільний `user_id`: власник приватної теми завжди береться з authenticated user, системний режим дозволений лише адміністраторам.
- Не використовувати `learning_profile_id` як власника теми. Прогрес окремий для кожного профілю, теми акаунта спільні.
- Звичайному користувачу системний варіант у UI **не показувати**, але це **не замінює** серверну перевірку. Підміна поля `scope=system` у запиті → відмова `403` і **жодних записів**.
- Системний імпорт **не повинен** змінювати жодних приватних тем; приватний імпорт **не повинен** змінювати чужих приватних або системних тем.

### 2.2. Адміністратори через серверну конфігурацію

За аналогією з SimpleCV: конфігураційний файл (орієнтир `config/admin.php`) отримує список email із `.env`, наприклад:

```dotenv
ADMIN_EMAILS=admin@example.com,second-admin@example.com
```

- Без нової колонки `users.is_admin`, ролей у БД та важкої бібліотеки permissions.
- За замовчуванням список **порожній**, тобто адміністративного доступу немає.
- Права має **лише автентифікований користувач із підтвердженим email**, якщо його нормалізована email-адреса точно входить до серверного списку; пробіли навколо значень списку і регістр email обробляти узгоджено.
- Список не віддавати у frontend, HTML, API чи логи. Ніколи не довіряти параметру `is_admin` від клієнта.
- Перевіряти право **на кожному запиті**, що стосується системного імпорту: при попередньому перегляді **і** фінальному підтвердженні; за час між ними права могли змінитися.
- Працювати з Laravel config та конфігураційним кешем; після зміни `ADMIN_EMAILS` на production може знадобитися стандартне оновлення config cache. Не редагувати секрети у Git.
- Перед реалізацією перевірити, чи вже є відповідний механізм в коді; **не дублювати** його за наявності.

### 2.3. Формат фактичного CSV

Зразок, який надав користувач:

```csv
word_en,word_uk,level,lesson,topic
city,місто,A1-A2,1,Greetings! Вітаю!
country,країна,A1-A2,1,Greetings! Вітаю!
```

- **Обов'язкові заголовки:** `word_en`, `word_uk`, `level`, `topic` (порядок довільний).
- **`lesson` — необов'язкова колонка:** допустима, **ігнорується повністю**. Не створювати `lesson_id`, таблицю уроків чи іншу прив'язку до `lesson`.
- `course`, `id`, `image_path`, `example_en`, `example_uk` та додаткові колонки **не потрібні**; зайві заголовки можна ігнорувати з повідомленням, не імпортувати їх мовчки в глобальні поля.
- CSV: UTF-8 (допустимий BOM), роздільник **кома**, коректні лапки/коми/переноси в quoted-полях, CRLF/LF. Не розбивати рядки звичайним `explode(',')`.
- Назва CSV-файлу довільна: **не** є ідентифікатором теми чи джерела. CSV завантажується через браузер; **не вимагати** папки `database/imports/`, Git commit або SSH.
- Невалідний файл, обов'язкова порожня клітинка, некоректний UTF-8, порушена довжина/формат → чітка помилка з номером CSV-рядка; **жодних часткових записів**.
- Установити розумні та документовані ліміти на розмір файлу/число рядків з урахуванням shared hosting, без важких пакетів/черг. Перший наданий CSV дуже невеликий.

**Контрольні дані фактичного зразка (лише орієнтир для тесту):** 180 рядків, 6 тем по 30 рядків, рівень `A1-A2`, 179 унікальних пар EN+UK; `friend — друг` є в двох темах, а у `People around. Люди навколо нас ` є пробіл наприкінці назви. Якщо цільові теми й словник порожні: **6 тем / 179 слів / 180 зв'язків**. Це не жорстко зашиті очікування для інших CSV.

### 2.4. Правила глобального словника й збереження

- Пара EN+UK глобально унікальна **після нормалізації**. Використовувати чинний `App\TextKeyNormalizer`, модель `Word` та DB-унікальність `(word_en_key, word_uk_key)`; не створювати власний альтернативний алгоритм нормалізації.
- **Різні переклади** одного EN-слова — різні глобальні картки. Ідентична пара в кількох темах — один `words.id` та кілька `topic_word`.
- `topics.level` і `topics.name` обробляються за чинними правилами моделі `Topic`; назви тем можуть повторюватися — **не додавати UNIQUE(level, name)**.
- Зв'язок `(topic_id, word_id)` є унікальним; повторний імпорт не повинен створювати його дубль.
- Під час імпорту **не** змінювати існуючі `word_en`, `word_uk`, `image_path`, `example_*`, не переписувати `word_progress` / `progress_sync_batches`, не переносити прогрес між картками.
- Не видаляти теми, глобальні слова чи зв'язки, якщо їх уже немає у наступному CSV; **не** використовувати `sync()` зі зняттям зв'язків. Імпорт **лише додає** відсутні сутності/зв'язки.
- Виправлення перекладу, редагування тем, видалення або «повна синхронізація з CSV» — окремі задачі з явними правилами, **не приховані опції імпорту**.
- Не віддавати користувачу чужі приватні теми/власників і не розкривати дані чужого приватного словника через попередній перегляд або звіт. Глобальний пошук дублюючих пар допустимий **всередині** імпортного сервісу, але не означає права на перегляд чужого контенту.

### 2.5. Відкрите рішення для Етапу 1 — ідентичність тем

**Критично:** архітектура дозволяє кілька `topics` з однаковими `level` і `name` у тому самому scope. CSV не має `topic_id` чи стабільного `topic_key`. Тому `firstOrCreate(['user_id' => ..., 'level' => ..., 'name' => ...])` **не гарантує** правильної ідентифікації тем для всіх випадків.

На Етапі 1 агент має **запропонувати одне просте безпечне рішення для обох scope**, узгодити його з власником **до реалізації**. Потрібно описати:

- як пов'язати тему з `topics.id` при першому й повторному завантаженні файлу;
- як працювати з однаковими назвами, приватними темами різних акаунтів, системними темами та імпортом різних CSV;
- як діяти, якщо тему перейменували або у файлі є дві логічно різні теми з однаковими `level + topic`;
- чи потрібний **необов'язковий** стійкий `topic_key`, збережене зіставлення джерела/теми, або явний вибір цільового `topics.id` у вебінтерфейсі;
- як гарантувати безпечний повторний імпорт і не породжувати дублікати при паралельних підтвердженнях.

**Можливий мінімальний варіант для обговорення, не затверджена реалізація:** у вибраному scope (`NULL` або поточний `user_id`) зіставляти `level + normalized topic name` тільки якщо існує **рівно одна** відповідна тема; за кількох збігів — **не імпортувати автоматично**, а показати неоднозначність та запропонувати явний вибір/стабільний ключ. Перейменування в CSV за цим підходом означає **нову** тему, а не редагування старої. Потрібно окремо продумати захист паралельних імпортів. Альтернатива — стійкі імпортні ключі/мапа, але це може вимагати змін схеми й/або формату CSV.

**Заборонено** мовчки зливати однойменні теми, непомітно змінювати схему, вимагати `lesson` як ідентифікатор, покладатися на ім'я CSV-файлу чи зберігати відповідність лише в непостійному файлі контейнера. Якщо без зміни архітектури або нового правила не гарантувати коректність — зупинитися й погодити її з власником. Поточний CSV має імпортуватися **без ручного редагування** після погодження механізму.

### 2.6. Вебсценарій: завантаження → перевірка → підтвердження

1. Користувач із підтвердженим email відкриває захищену сторінку **«Імпорт слів»**.
2. Вибирає `.csv`; звичайному користувачу доступний тільки приватний режим. Адміністратору — вибір **«Приватні» (default) / «Системні»**.
3. Натискає **«Перевірити файл»**. Backend перевіряє права, формат, вміст і можливі конфлікти; показує безпечний попередній перегляд **без запису тем/слів у БД**.
4. Відображаються зрозумілі лічильники (рядки, теми, унікальні пари, потенційні нові зв'язки, пропуски/дублікати, помилки), **обраний тип** імпорту та за потреби неоднозначності, які треба вирішити. Не показувати, які слова належать чужим приватним темам.
5. Якщо помилки або нерозв'язані неоднозначності — кнопка підтвердження недоступна. Якщо все коректно — користувач явно натискає **«Імпортувати»**; для системного режиму зробити помітне додаткове підтвердження.
6. Backend **знову** перевіряє права, зв'язок завантаження з користувачем/режимом, цілісність і чинні DB-умови; записує атомарно й повертає фактичний звіт. Застарілий preview не є авторизацією й не гарантує, що БД не змінилася.

**Безпека тимчасового файлу:** завантажений CSV обробляти із серверного тимчасового/приватного storage, **не** з `public/`; унеможливити підміну файлу, користувача чи `scope` між preview та confirm (наприклад, короткоживучий session-bound token + hash і повторна серверна валідація). Визначити строк життя та видалення/очищення тимчасових файлів; не зберігати вихідні CSV назавжди й не робити їх публічними. Не використовувати тільки передані клієнтом лічильники/ID як джерело істини.

**Технічні межі:** серверні маршрути `auth` + `verified`, CSRF для POST, перевірки прав у preview та confirm; frontend у чинному стилі mobile-first, із уже реалізованими `system/light/dark`. Використати наявний Laravel/Blade/Vue + TypeScript; **не** додавати зайвих залежностей чи нових Docker-сервісів.

## 3. Правила виконання task — обов'язково для агента

**Виконувати строго поетапно. Одна ітерація = один ПОВНИЙ етап, а не один пункт у ньому.**

1. Після вказівки користувача виконати **всі доступні пункти тільки поточного етапу**, включно з реалізацією, тестами й коротким записом результатів; не просити окремий дозвіл після кожного чекбокса.
2. **Після завершення або блокування етапу зупинитися.** Наступний етап починати **тільки після нової прямої команди користувача**.
3. Ставити `[x]` **лише якщо пункт реально виконаний і перевірений**; неперевірене або заблоковане лишати `[ ]`.
4. **Під відповідним етапом** заповнювати `Implementation notes`: змінені файли, команди та результати, прийняті рішення, обмеження/блокери. Не видаляти вимоги або нотатки попередніх етапів; не вести окремий великий журнал.
5. Після етапу коротко повідомити результат, тести та неперевірене, запропонувати **коротку Git commit message англійською**. **Не робити `git commit` чи `git push` без прямої вказівки.** Назвати наступний етап, **не починати** його, та порадити, чи варто відкрити нову сесію агента.
6. Перед непогодженою зміною моделі даних, Docker, Composer/npm-залежностей, формату CSV або принципу ідентифікації тем — **зупинитися, описати варіанти й запитати дозвіл**. Не розширювати обсяг функціоналу.
7. Якщо змінено таблиці, поля, індекси, FK, Eloquent-зв'язки або правила збереження, **в тому самому етапі** оновити `docs/architecture/data-model.md`. Погоджені зміни користувацької поведінки відобразити також у `docs/business/english-flashcards-business-logic-v0.4.md`. Уже затверджена зміна MVP щодо **приватного вебімпорту** має бути внесена в обидва документи там, де старі формулювання їй суперечать; не створювати паралельних файлів «v2».
8. Усі PHP/Composer/Node/Artisan-команди — **через наявний Docker Compose** у WSL2, без установлення інструментів у Ubuntu. Не змінювати Docker/залежності без погодження.
9. Тести з БД — **лише на окремій MySQL `english_cards_test`**, після перевірки фактичної конфігурації. `RefreshDatabase` — тільки на test-БД. **Не** виконувати `migrate:fresh`, `db:wipe`, `truncate` чи видалення Docker volumes на dev/production. Production не чіпати. Реальний імпорт у dev-БД — тільки після **окремої явної вказівки** власника, не як наслідок тестів або перегляду форми.

## 5. Definition of Done

Task завершено лише якщо:

- Усі **5 етапів** виконані, чекбокси відповідають фактам, `Implementation notes` заповнені під кожним етапом.
- Є **єдина сторінка вебімпорту**, де звичайний користувач завантажує CSV у **свої приватні теми**, а адміністратор може окремо вибрати **власні приватні** або **системні** теми; admin default — приватний.
- Адміністратор визначається **тільки** через перевірений email і серверну конфігурацію; підміна запиту не відкриває системний імпорт чи доступ до чужих приватних тем.
- Зразок CSV читається **без редагування й видалення `lesson`**, помилки мають номери рядків; preview не записує теми/слова/зв'язки.
- Ідентичність тем між імпортами **погоджена і протестована**; неоднозначні назви не зливаються мовчки, а перейменування не спричиняє непогодженої зміни існуючої теми.
- У чистій цільовій частині БД імпорт зразка дає **6 тем / 179 глобальних слів / 180 зв'язків**; повтор тієї самої операції — **0 додаткових тем, слів та зв'язків**. При використанні вже існуючих глобальних карток лічильники нових слів коректно відрізняються.
- Імпорт не перезаписує глобальні слова, не скидає прогрес, не видаляє відсутні в CSV дані; невалідний файл і збій запису не лишають часткових змін.
- Preview/confirm захищені CSRF/auth/verified, перевіркою scope, цілісністю тимчасового файлу, серверною перевіркою перед записом; preview не розкриває приватних даних інших акаунтів.
- Тести пройшли на окремій MySQL-БД, фронтенд зібраний, документація оновлена, dev/production не змінені без прямого доручення; **немає** зайвих CLI/адмінпанелі/ролей/черг/CRUD.
