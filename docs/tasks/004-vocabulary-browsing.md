## 1. Мета та очікуваний результат

Реалізувати вебінтерфейс перегляду доступних тем і слів English Cards для авторизованих користувачів.

Користувач повинен мати можливість:

- Переглянути список доступних йому тем.
- Побачити назву, рівень, тип і кількість слів кожної теми.
- Відфільтрувати теми за рівнем та типом.
- Відкрити окрему тему.
- Переглянути всі слова цієї теми з англійськими назвами та українськими перекладами.
- Зручно користуватися сторінками на смартфоні та комп'ютері.

**Результат після всіх етапів:** після входу користувач відкриває сторінку «Теми», бачить усі доступні системні та власні приватні теми, вибирає потрібну й переглядає її словник.

Інтерфейс використовує наявну систему авторизації, модель даних і стилі оформлення.

## 2. Погоджена поведінка

### 2.1. Доступ до тем

У застосунку існують два типи тем:

| Тип | Значення `topics.user_id` | Доступ |
|---|---|---|
| Системна | `NULL` | Усі авторизовані користувачі з підтвердженим email |
| Приватна | ID користувача | Лише власник акаунта |

Правила:

- Користувач бачить усі системні теми.
- Користувач бачить власні приватні теми.
- Приватні теми інших акаунтів недоступні.
- Адміністратор також бачить лише системні та **власні** приватні теми.
- Адміністративні права на системний імпорт не надають права переглядати чужі приватні теми.
- Усі навчальні профілі одного акаунта мають доступ до тих самих приватних тем.
- Для перегляду словника не потрібно використовувати `learning_profile_id` як власника теми.
- Наявність або відсутність активного навчального профілю не повинна змінювати доступність тем.

Доступ повинен перевірятися на сервері.

**Захист прямих URL:**

Якщо користувач звертається до приватної теми іншого акаунта, сервер повинен повернути `404`.

Не розкривати назву, кількість слів, власника або інші дані недоступної теми.

Підміна `user_id`, `scope` чи інших query-параметрів не повинна дозволяти отримувати чужі дані.

### 2.2. Глобальний словник

За погодженою архітектурою:

- `words` — спільний глобальний словник.
- `topics` — системні або приватні теми.
- `topic_word` — зв'язки між темами та словами.

Одне глобальне слово може входити до кількох тем.

Для перегляду словника використовуються зв'язки конкретної доступної теми.

**Не створювати окремий загальний екран усіх записів `words`, незалежно від тем.**

Користувач не повинен отримувати доступ до глобальних слів, які не належать жодній доступній йому темі, через новий маршрут Task 004.

Однакові слова в різних темах не потрібно об'єднувати або приховувати: кожна тема відображає власний набір зв'язків.

Перегляд не змінює записи `words`, `topics`, `topic_word` або прогрес користувачів.

### 2.3. Сторінка «Теми»

Створити окрему сторінку зі списком доступних тем.

**Основні елементи:**

- Заголовок «Теми».
- Короткий пояснювальний текст.
- Фільтр за типом.
- Фільтр за рівнем.
- Список тем.
- Кількість слів у кожній темі.
- Можливість відкрити тему.
- Зрозумілий стан, коли відповідних тем немає.

#### Інформація про тему

Кожен елемент списку повинен містити:

| Поле | Приклад |
|---|---|
| Назва | Greetings! Вітаю! |
| Рівень | A1-A2 |
| Тип | Системна / Приватна |
| Кількість слів | 30 |
| Дія | Переглянути |

Можна зробити всю картку теми клікабельною, якщо це не погіршує доступність і навігацію з клавіатури.

#### Фільтри

**За типом:**

- Усі — за замовчуванням.
- Системні.
- Приватні.

**За рівнем:**

- Усі рівні — за замовчуванням.
- Доступні рівні з фактичних тем користувача.

Не створювати жорстко закодований перелік рівнів, який суперечить актуальній бізнес-логіці.

Фільтри повинні працювати разом.

Наприклад: користувач вибирає «Приватні» та «A1-A2» і бачить тільки свої приватні теми відповідного рівня.

Застосування фільтрів не повинно розкривати інформацію про чужі теми, включно зі списком доступних значень фільтра.

Реалізація може використовувати звичайні GET-параметри без складного JavaScript.

Параметри необхідно перевіряти на сервері.

#### Сортування

За замовчуванням теми сортуються за **`topics.id ASC`** — у порядку створення записів.

Порядок не залежить від назви теми й залишається стабільним між сторінками та при фільтрації. Це рішення власника від 03.11.2026 замінює початкове сортування за назвою; окреме поле порядку поки не додається.

Однакові назви тем дозволені поточною моделлю даних.

**Не об'єднувати теми лише через однакову назву.**

Кожна тема має власний ID і відображається окремо.

Тип та рівень допомагають користувачу розрізняти теми.

#### Порожні теми

Тему без слів також потрібно показувати.

Для неї відображається:

`0 слів`

Така тема повинна відкриватися, але її сторінка показує повідомлення про відсутність слів.

#### Кількість слів

Кількість визначається за фактичними зв'язками `topic_word`.

Не використовувати кількість рядків останнього CSV-імпорту.

Не рахувати прогрес навчальних профілів.

Уникати N+1-запитів.

За потреби використовувати наявні Eloquent-зв'язки й `withCount()`.

#### Пагінація

Передбачити серверну пагінацію списку тем:

- **20 тем на сторінку**.
- Збереження параметрів фільтрації під час переходу між сторінками.
- Коректна робота, якщо тем менше ніж 20.
- Відсутність завантаження всього списку тем у пам'ять лише для відображення однієї сторінки.

Не додавати сторонніх бібліотек для таблиць або пагінації.

### 2.4. Сторінка перегляду теми

Після вибору теми користувач відкриває її словник.

**Загальна інформація:**

- Назва теми.
- Рівень.
- Тип: системна або приватна.
- Загальна кількість слів.
- Посилання «Назад до тем».

**Список слів:**

| English | Українська |
|---|---|
| city | місто |
| country | країна |
| friend | друг |

Відображати фактичні значення `words.word_en` та `words.word_uk`.

Не застосовувати ключі `word_en_key` / `word_uk_key` для формування відображуваних текстів.

Ключі нормалізації використовуються для порівняння та забезпечення унікальності, але не замінюють оригінальні значення.

#### Поведінка списку

- Показувати всі слова, пов'язані з темою.
- Не показувати слова інших тем, якщо вони не пов'язані з поточною.
- Не показувати дублікати того самого `words.id` у межах однієї теми.
- Відображати EN та UK одночасно.
- Не приховувати переклад за натисканням.
- Не додавати кнопки навчання або перевірки.
- Не змінювати `word_progress`.
- Не використовувати статус знання слова як фільтр.

Для стабільного порядку слова сортувати за `word_en` з додатковим сортуванням за `words.id`.

#### Пагінація слів

Передбачити:

- **30 слів на сторінку**.
- Звичайну серверну пагінацію.
- Коректну роботу для тем із менш ніж 30 словами.
- Стабільний порядок між сторінками.

Пагінація не повинна впливати на загальний лічильник слів у темі.

#### Майбутні поля словника

Модель `Word` уже може містити:

- `image_path`
- `example_en`
- `example_uk`

У межах Task 004 не потрібно створювати окремий UI для зображень або прикладів.

Показувати лише англійське слово й український переклад.

Додаткові поля залишаються для наступних етапів розвитку застосунку.

### 2.5. Навігація

Додати пункт **«Теми»** до наявної навігації авторизованого користувача.

Не створювати другу навігаційну систему.

Використати наявний layout та компоненти оформлення.

Забезпечити зрозумілий перехід:

**Навігація → Теми → Перегляд теми → Назад до тем**

Якщо користувач застосував фільтри та відкрив тему, бажано зберігати можливість повернення до списку з тими самими фільтрами.

Реалізувати це без перенесення логіки авторизації до клієнтського JavaScript.

На сторінці списку тем можна передбачити посилання **«Імпорт слів»** до вже реалізованого Task 003.

Використовувати чинний маршрут імпорту, не дублювати його функціонал.

### 2.6. Інтерфейс і адаптивність

Використовувати поточний mobile-first дизайн English Cards.

Підтримувати:

- Системну тему оформлення.
- Світлу тему.
- Темну тему.
- Мобільні екрани від 320 px.
- Типові смартфони близько 390 px.
- Планшети.
- Desktop.

**Список тем:** рекомендовано адаптивні картки або інше просте представлення відповідно до наявного стилю.

**Список слів:** на desktop допустима таблиця з двома колонками; на смартфоні — компактні рядки або картки без горизонтального прокручування сторінки.

Уникати складних таблиць із великою кількістю колонок.

Дотримуватися чинних кольорів, типографіки, відступів, кнопок та стилів.

Передбачити:

- Видимий keyboard focus.
- Зрозумілі підписи фільтрів.
- Достатній контраст.
- Коректне перенесення довгих назв тем і слів.
- Відсутність горизонтального прокручування на мобільних екранах.
- Коректні порожні стани.
- Зрозумілі активні стани навігації.

Не встановлювати нову UI-бібліотеку.

## 3. Технічні обмеження

### 3.1. Backend

Використовувати чинний Laravel 13.

Перевага надається простій реалізації через:

- Laravel Routes.
- Controllers.
- Eloquent.
- Blade.
- Наявні компоненти та стилі.

Vue/TypeScript використовувати лише якщо це виправдано фактичною frontend-архітектурою.

Не створювати окремий API тільки заради двох сторінок перегляду.

Не використовувати raw SQL там, де достатньо Eloquent.

### 3.2. Безпека

Маршрути перегляду повинні використовувати:

- `auth`
- `verified`

Правила доступу до тем реалізувати централізовано, щоб їх можна було повторно використовувати в майбутніх задачах навчання.

Перед створенням нових класів перевірити наявні механізми доступу.

**Не дублювати логіку перевірки власника теми в кількох контролерах.**

Перевірки повинні гарантувати:

- Доступ до системних тем.
- Доступ до приватних тем власника.
- Відмову в доступі до чужих приватних тем.
- Відсутність витоків даних через лічильники та фільтри.
- Відсутність можливості обійти обмеження через прямі URL.

Для недоступної теми повертати `404`.

### 3.3. База даних

Використовувати наявні таблиці:

- `topics`
- `words`
- `topic_word`

Не додавати нові таблиці, колонки, індекси або міграції без окремого погодження.

Не змінювати чинну нормалізацію назв і слів.

Не змінювати механізм імпорту Task 003 без технічної необхідності та погодження.

### 3.4. Тестове середовище

Усі DB-тести запускати виключно на окремій MySQL:

`english_cards_test`

Перед тестами агент повинен перевірити фактичну конфігурацію підключення.

Використовувати чинний тестовий підхід Laravel/PHPUnit.

Заборонено:

- `migrate:fresh` на dev/production.
- `db:wipe` на dev/production.
- Видалення Docker volumes.
- Імпорт тестових CSV у dev/production без дозволу.
- Зміну реальних користувачів, тем або прогресу на dev/production під час тестування.

PHP, Composer, Node та Artisan запускати через наявний Docker Compose.

Docker і залежності не змінювати без погодження.

## 6. Definition of Done

Task 004 вважається завершеним, якщо:

- Усі чотири етапи виконані та задокументовані.
- Користувач має сторінку «Теми» в основній навігації.
- Системні теми доступні всім авторизованим користувачам із підтвердженим email.
- Приватні теми доступні тільки власнику акаунта незалежно від активного навчального профілю.
- Адміністратор не отримує доступу до чужих приватних тем.
- Список показує назву, рівень, тип і правильну кількість слів кожної теми.
- Працюють фільтри за типом і рівнем.
- Працюють сортування та пагінація тем.
- Однакові назви тем не призводять до об'єднання різних записів.
- Можна відкрити окрему тему та переглянути всі пов'язані з нею слова.
- Слова показуються англійською та українською.
- Працює пагінація слів.
- Недоступна приватна тема повертає `404` без розкриття її даних.
- Перегляд не змінює словник, зв'язки чи прогрес.
- Сторінки використовують чинний адаптивний дизайн і підтримують усі три режими оформлення.
- Тести пройшли на окремій MySQL-БД.
- Frontend build та перевірки форматування пройшли.
- Документація актуалізована.
- Не створено зайвих міграцій, залежностей, API, адміністративних панелей або функціоналу поза Task 004.
- Dev/production дані не змінювалися без окремого дозволу.
