# Task 007 — Збереження прогресу

**Проєкт:** English Cards  
**Статус:** Заплановано  
**Залежність:** Task 006 — режим «Перевірка»

## 1. Мета

Реалізувати надійне збереження результатів перевірки слів для кожного навчального профілю.

Після проходження перевірки користувач повинен отримувати оновлені рівні знання слів. Результати не повинні губитися через тимчасову втрату інтернету або повторно застосовуватися через дублювання запитів.

Використати наявні таблиці:

- `word_progress`
- `progress_sync_batches`

Не створювати нових таблиць без обґрунтованої необхідності та попереднього погодження.

## 2. Правила бізнес-логіки

### Рівні знання

| Рівень | Значення |
|---|---|
| 0 | Нове або незнайоме слово |
| 1 | Один раз підтверджено «Знаю» |
| 2 | Двічі підтверджено «Знаю» |
| 3 | Тричі підтверджено «Знаю», умовно засвоєне |

Правила зміни прогресу:

- «Знаю» у першому колі → збільшити рівень на 1, максимум до 3.
- «Не знаю» у першому колі → скинути рівень до 0.
- «Знаю» або «Не знаю» під час повторного кола → рівень залишається 0.
- Одне слово може отримати максимум одне підвищення за сесію.
- Відсутній запис у `word_progress` означає рівень 0.
- Перегляд карток у режимі «Навчання» не змінює прогрес.
- Повторне проходження перевірки створює нову сесію.
- Рівень знання одного слова спільний між темами в межах одного навчального профілю.
- Різні навчальні профілі мають незалежний прогрес.

### Збереження відповідей

- Після кожної відповіді зберігати стан перевірки локально в IndexedDB.
- Після завершення перевірки надсилати відповіді одним пакетом до Laravel.
- Сервер самостійно розраховує нові рівні знання.
- Не довіряти готовим значенням `knowledge_level` із браузера.
- Повторне надсилання того самого пакета не повинно повторно змінювати прогрес.
- Не видаляти локальний пакет, доки сервер не підтвердив його успішну обробку.

### Перервані перевірки

Якщо користувач закрив браузер під час перевірки:

- Зберегти вже надані відповіді.
- Під час наступного відкриття застосунку виявити незавершену сесію.
- Закрити її як перервану та синхронізувати надані відповіді.
- Не вважати картки без відповідей такими, що отримали «Не знаю».
- Нову перевірку починати з новим UUID.

### Історія

Повну історію проходжень у MVP не зберігати.

`progress_sync_batches` використовувати для захисту від повторного застосування пакетів і збереження короткого результату синхронізації.

Розширена історія, статистика за датами та графіки — поза межами Task 007.

- [ ] Перевірити реалізацію Task 006: формування сесій, відповіді, повторне коло та екран результатів.
- [ ] Перевірити моделі `WordProgress`, `ProgressSyncBatch` та наявні міграції.
- [ ] З'ясувати, як зараз зберігається стан перевірки у браузері.
- [ ] Визначити формат HTTP-запиту та відповіді для синхронізації.
- [ ] Передбачити UUID сесії, ID навчального профілю, відповіді першого й повторного кола та ознаку завершеної/перерваної перевірки.
- [ ] Визначити обмеження розміру пакета, валідацію та обробку недоступних слів.
- [ ] Перевірити можливість реалізації без нових таблиць і міграцій.
- [ ] Зафіксувати технічне рішення та необхідні зміни у task-файлі.

**На цьому етапі не змінювати бізнес-логіку, UI та структуру БД.**

### Етап 2. Серверна обробка прогресу

**Результат:** Laravel приймає пакет відповідей, перевіряє його та безпечно оновлює рівні знання.

- [ ] Реалізувати захищений HTTP endpoint синхронізації.
- [ ] Перевіряти авторизацію та належність `learning_profile_id` поточному користувачеві.
- [ ] Перевіряти формат UUID, відповідей, унікальність `word_id` та допустимість повторного кола.
- [ ] Враховувати лише слова, доступні користувачеві через системні або власні приватні теми.
- [ ] Недоступні або видалені слова пропускати з відображенням їхніх ID у результаті.
- [ ] Реалізувати обчислення `knowledge_level` за правилами розділу 2.
- [ ] Реалізувати ідемпотентність через `progress_sync_batches`.
- [ ] Для повторного UUID з тим самим вмістом повертати попередній результат без зміни прогресу.
- [ ] Для повторного UUID з іншим вмістом повертати `409 Conflict`.
- [ ] Виконувати перевірку дублювання, зміну прогресу та фіксацію обробленого пакета в одній транзакції.
- [ ] Захистити конкурентні запити від подвійного підвищення рівнів і втрати оновлень.
- [ ] Додати Feature/Unit-тести серверної логіки.

### Етап 3. Локальне збереження в IndexedDB

**Результат:** відповіді перевірки зберігаються в браузері до підтвердженої синхронізації.

- [ ] Реалізувати локальне збереження сесії з UUID, `user_id`, `learning_profile_id` та відповідями.
- [ ] Зберігати кожну відповідь до переходу до наступної картки.
- [ ] Забезпечити коректне оновлення локального стану, якщо користувач змінює відповідь у межах дозволеної навігації.
- [ ] Після завершення перевірки формувати незмінний пакет для синхронізації.
- [ ] При втраті зв'язку зберігати пакет для повторного надсилання.
- [ ] Після підтвердження Laravel видаляти відповідний локальний пакет.
- [ ] Після перезавантаження сторінки або повторного відкриття застосунку виявляти незавершені сесії.
- [ ] Реалізувати синхронізацію перерваних сесій без додавання відповідей за непройдені картки.
- [ ] Не змішувати локальні результати різних акаунтів і навчальних профілів.
- [ ] Надсилати пакети одного профілю послідовно, у порядку їх створення.
- [ ] Передбачити повідомлення про помилки локального збереження та синхронізації.

### Етап 4. Інтеграція з режимом «Перевірка»

**Результат:** наявний режим перевірки повністю використовує новий механізм збереження прогресу.

- [ ] Підключити локальне збереження до кнопок «Знаю» та «Не знаю».
- [ ] Підключити пакетну синхронізацію після завершення перевірки.
- [ ] Зберегти чинну логіку першого та повторного кола.
- [ ] Зберегти поточні показники екрана результатів.
- [ ] Передбачити зрозумілий стан синхронізації: збережено, очікує надсилання, помилка.
- [ ] Не показувати успішне серверне збереження до отримання підтвердження.
- [ ] Забезпечити можливість повторної синхронізації після тимчасової помилки.
- [ ] Переконатися, що повторне натискання кнопок або запитів не створює дублікати відповідей.
- [ ] Перевірити проходження повторної перевірки з новим UUID.
- [ ] Не змінювати дизайн карток, фільтри, вибір тем та навігацію, окрім мінімальних елементів, необхідних для відображення стану синхронізації.

### Етап 5. Перевірки та завершення

**Результат:** збереження прогресу перевірене на основних і граничних сценаріях.

Перевірити:

- [ ] «Знаю»: `0 → 1 → 2 → 3 → 3` у послідовних окремих сесіях.
- [ ] «Не знаю»: скидання будь-якого рівня до 0.
- [ ] «Не знаю» в першому колі та «Знаю» в повторному: рівень залишається 0.
- [ ] Повторне надсилання однакового пакета не змінює прогрес.
- [ ] Той самий UUID з іншими відповідями повертає `409`.
- [ ] Конкурентні запити не спричиняють подвійного застосування.
- [ ] Прогрес одного навчального профілю не змінює прогрес іншого.
- [ ] Неможливо синхронізувати результати для чужого профілю.
- [ ] Неможливо записати прогрес для недоступних слів.
- [ ] Слова, що входять у декілька тем, не дублюються.
- [ ] Переривання перевірки не створює відповідей для непройдених карток.
- [ ] Втрата зв'язку не призводить до видалення локального пакета.
- [ ] Повторне відкриття застосунку дозволяє доставити незбережені результати.
- [ ] Синхронізація працює після перемикання активного профілю, не змінюючи власника пакета.
- [ ] Режим «Навчання» не змінює `word_progress`.
- [ ] Наявні тести режиму «Перевірка» продовжують проходити.

Виконати:
- [ ] Релевантні та повні автоматизовані тести в окремій тестовій БД.
- [ ] Laravel Pint.
- [ ] Збірку frontend.
- [ ] `git diff --check`.
- [ ] Доступні браузерні перевірки на мобільних і десктопних розмірах.
- [ ] Оновлення документації, якщо фактичний API-контракт або реалізація цього потребують.

## 4. Обмеження

1. Не змінювати структуру БД без попереднього погодження.
2. Не створювати нових таблиць для історії проходжень.
3. Не додавати Redis, черги, WebSocket або інші серверні залежності.
4. Не реалізовувати повну офлайн-роботу застосунку.
5. Не змінювати алгоритм «Перевірки», погоджений у Task 006.
6. Не змінювати логіку режиму «Навчання».
7. Не додавати статистику на `/home` — це окреме наступне завдання.
8. Не реалізовувати ручне скидання прогресу в межах цього task.
9. Не переробляти наявний дизайн без необхідності.
10. Не видаляти технічні записи `progress_sync_batches` автоматично.

## 6. Критерії завершення Task 007

Завдання вважається виконаним, коли:

- Результати перевірок надійно передаються з браузера до Laravel.
- Рівні знання зберігаються для відповідного навчального профілю.
- Повторні пакети не призводять до подвійної зміни прогресу.
- Тимчасові помилки з'єднання не призводять до втрати вже локально збережених відповідей.
- Перервані перевірки обробляються коректно.
- Усі необхідні тести проходять.
- Документація відповідає фактичній реалізації.
